doing these runs. Because when we start testing other business models and
making changes to BLAM8 so they work, we have to make sure we are VERY careful
with stuff that works already in other models. Always being agnostic as
possible."

**What this list is.** Every behaviour here was watched working end to end on
a live tenant, and has at least one test that fails if it breaks. It is the
thing to check BEFORE changing shared code for a new business type.

**How to use it.**

1. Before a change for one business type, find the rows it could touch (the
   `Surface` column) and read their tests. If the change needs a row's
   behaviour to differ, that is a product decision to raise, not a test to edit.
2. A new behaviour proven on a run gets a row the same day, with the commit,
   the evidence (a film, a run doc, a thread) and the test that pins it.
3. A row whose test is `—` is a gap: proven by eye only. Close those first.
4. **Agnostic first.** Each row says what the behaviour is in the product's
   words (a *dependant*, a *stay*, a *gated date*), not the vertical's (a dog,
   a kennel, a jab). If a fix only makes sense for one vertical, it belongs in
   that tenant's settings, not in the core.

Columns: **Behaviour** (what a customer or owner sees) · **Proven on** (type,
tenant, date, evidence) · **Guard** (tests) · **Surface** (the code it lives in).
